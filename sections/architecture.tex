    \centering
    \includegraphics[width=\textwidth]{pics/datasource-architecture.png}
    \caption{Die Architektur des Grafana Plugins}
    \label{fig:datasource-architecture}
\end{figure}

Global Infrastructure Overview besteht aus einem selbstentwickelten \gls{grafana}-Plugin,
wie in Abschnitt~\ref{subsec:grafana-plugins} beschrieben. Ein eigenständiges Plugin wurde
gewählt, da die für diese Arbeit benötigte, standortbasierte und kartenartige Darstellung
mehrerer heterogener Datenquellen mit den standardmäßig verfügbaren \gls{grafana}-Panels
und -Datenquellen nicht abgebildet werden kann. Zur Entwicklung wurde das offizielle
\gls{grafana} Plugin SDK verwendet, das über die \gls{grafana} Plugin Tools bereitgestellt
wird~\cite{grafana2026plugintools}.

Dieses knüpft an die bestehende \gls{grafana}-Struktur an und nutzt bestehende Datenquellen,
die in Abschnitt~\ref{sec:defined-sources} beschrieben sind. Des Weiteren wurde das Plugin zu
einer bestehenden \gls{grafana}-Instanz hinzugefügt, die über \gls{helm} bereitgestellt wird,
wie in Abbildung~\ref{fig:datasource-architecture} dargestellt ist. Der Einsatz von \gls{helm}
ermöglicht dabei eine versionierte, wiederholbare Bereitstellung der \gls{grafana}-Instanz
über verschiedene Umgebungen hinweg~\cite{helm2026intro}.

Die einzelnen Systemelemente übernehmen folgende Aufgaben:
\begin{compactitem}
    \item \textbf{Weboberfläche:} Stellt die Konfigurations- und Anzeigeoberfläche des
    \gls{grafana}-Plugins innerhalb von \gls{grafana} bereit~\cite{grafana2026plugintools}.

    \item \textbf{Plugin-Manager:} Verwaltet den Lebenszyklus des Plugins und leitet
    Anfragen der Weboberfläche über \gls{grpc} an das Backend weiter~\cite{grafana2026backendplugins}.

    \item \textbf{gRPC-Server:} Nimmt die vom Plugin-Manager gesendeten Anfragen entgegen
    und verteilt sie an die zuständigen Backend-Komponenten~\cite{grafana2026backendplugins}.

    \item \textbf{Abfrageverarbeitung:} Verarbeitet Abfragen und ruft dafür Endpunkte der
    externen Systeme ab~\cite{grafana2026backendplugins}.

    \item \textbf{Ressourcenverarbeitung:} Stellt eigene, vom Plugin definierte
    HTTP-Ressourcen und -Endpunkte bereit~\cite{grafana2026backendplugins}.

    \item \textbf{Zustandsprüfung:} Überprüft die Verfügbarkeit und Funktionsfähigkeit
    des Plugins~\cite{grafana2026backendplugins}.

    \item \textbf{Datenquellen-Verwaltung:} Verwaltet den Zugriff auf die konfigurierten
    Datenquellen (siehe Abschnitt~\ref{subsec:grafana-datasources}) sowie den zugehörigen
    \gls{grafana}-Cache.

    \item \textbf{Grafana-Cache:} Speichert zwischenzeitlich abgerufene Daten, um wiederholte
    Anfragen an externe Systeme zu reduzieren. Bei einer erneuten, identischen Abfrage werden die
    Ergebnisse aus dem Cache anstelle der Datenquelle zurückgegeben~\cite{grafana2026datasourcecaching}.

    \item \textbf{Externe Systeme:} Umfassen unter anderem den Silverpeak Orchestrator, der
    über \gls{rest} angesprochen wird, wie in Abschnitt~\ref{subsec:silverpeak-api}
    beschrieben.

    \item \textbf{Externe Datenquellen:} Umfassen die APIs von Zabbix, Silverpeak und
    Meraki (siehe Abschnitte~\ref{sec:zabbix}, \ref{sec:silverpeak} und \ref{sec:meraki})
    sowie die zugehörigen Datenbanken, aus denen die überwachten Metriken und
    Konfigurationsdaten bezogen werden.

    \item \textbf{Grafana-Nutzerverwaltung:} \gls{grafana} bietet eine integrierte Verwaltung
    von Benutzer:innen und Teams an, auf die über die \gls{grafana}-HTTP-API zugegriffen werden
    kann~\cite{grafana2026usermanagement,grafana2026httpapi}.
\end{compactitem}

Die Systemelemente, die über \gls{grafana} selbst bereitgestellt werden – die
Datenquellen, wie in Abschnitt~\ref{subsec:grafana-datasources} beschrieben, sowie die
Nutzerverwaltung – werden dabei direkt vom Plugin über die \gls{grafana}-HTTP-API
angesprochen. Dies ermöglicht ein effizientes Caching der \gls{grafana} eigenen Daten und schützt
gleichzeitig davor, dass sensible Informationen wie Zugangsdaten anderen Plugins oder
Diensten direkt zugänglich gemacht werden.

Des Weiteren können alle Systemelemente, die \gls{grafana} bereitstellt, von dort aus
konfiguriert werden. Die externen Datenquellen wie \gls{zabbix}, \gls{silverpeakcompany}
oder \gls{merakicompany} müssen hingegen über den jeweiligen Anbieter konfiguriert werden,
wie in den Abschnitten~\ref{sec:zabbix}, \ref{sec:silverpeak} und \ref{sec:meraki}
beschrieben. Die Datenbankquellen müssen für das \gls{grafana}-Netzwerk zugänglich sein.

Das \gls{grafana}-Backend hat die Aufgabe, Authentifizierung und Autorisierung für
\gls{silverpeakcompany} anzubieten, da \gls{silverpeakcompany} die Authentifizierung über
ein \gls{sessioncookie} regelt, wie in Abschnitt~\ref{subsec:silverpeak-api} beschrieben.
\gls{grafana} selbst bietet keine Möglichkeit, mit einem sitzungsbasierten System zu
kommunizieren, sondern unterstützt lediglich statische Zugangsdaten je
Datenquelle~\cite{grafana2026datasources}. Des Weiteren verarbeitet das
\gls{grafana}-Backend über die Ressourcenverarbeitung Abfragen, die für \gls{grafana}
selbst bestimmt sind und unabhängig von einer einzelnen Datenabfrage global genutzt werden
können~\cite{grafana2026backendplugins}. Die Zustandsprüfung gibt den derzeitigen Status
des Plugins an~\cite{grafana2026backendplugins}.

\section{Informationswege}
\label{sec:info-ways}

Eine Anfrage nach Daten einer der in Abschnitt~\ref{sec:defined-sources} beschriebenen
Datenquellen durchläuft dabei folgende Schritte:

\begin{compactenum}
    \item Die Weboberfläche sendet eine Anfrage an den Plugin-Manager.

    \item Der Plugin-Manager leitet die Anfrage direkt an die Datenquellen-Verwaltung
    weiter.

    \item Liegt ein gültiger Cache-Eintrag vor, werden die zwischengespeicherten Daten
    zurückgegeben. Andernfalls ruft die Datenquellen-Verwaltung die entsprechende externe
    Datenquelle ab und speichert das Ergebnis anschließend im Cache.

    \item Die abgerufenen Daten werden über denselben Weg an die Weboberfläche
    zurückgegeben und dort dargestellt.
\end{compactenum}

Das Plugin nutzt dabei ausschließlich die in \gls{grafana} konfigurierten Datenquellen, um auf
externe Systeme zuzugreifen. Dadurch werden Konfiguration und Zugangsdaten zentral über
\gls{grafana} verwaltet, ohne dass das Plugin selbst mit sensiblen API-Zugangsdaten in Berührung
kommt.

\subsection{Reaktionszeiten}
\label{subsec:reaction-times}

Bei der Entwicklung eines Plugins spielt auch die Reaktionszeit beim Laden der Daten eine wichtige
Rolle. Nach den von der \gls{nngroup} definierten Reaktionszeitgrenzen gilt eine Antwortzeit von bis
zu einer Sekunde als Obergrenze, um den Gedankenfluss der Nutzer:innen nicht zu unterbrechen, auch
wenn die Verzögerung bereits wahrgenommen wird. Ab einer Wartezeit von etwa zehn Sekunden ist
hingegen mit einem Abbruch der Aufgabe durch die Nutzer:innen zu rechnen~\cite{nielsen2026responsetimes}.

Da \gls{grafana} unter anderem zur nahezu echtzeitfähigen Darstellung von Monitoring-Daten
eingesetzt wird~\cite{VBondar2025}, ist eine geringe Reaktionszeit beim Laden der Daten essenziell,
um Nutzer:innen zeitnah einen aktuellen Überblick über den Zustand der überwachten Standorte und
Systeme zu ermöglichen.

Da das Plugin Daten aus mehreren, voneinander unabhängigen externen Systemen bezieht (siehe
Abschnitt~\ref{sec:defined-sources}), wurde bewusst eine virtuelle statt einer physischen
Datenintegration gewählt: Die Daten werden bei jeder Anfrage direkt aus den jeweiligen
Quellsystemen abgerufen, anstatt sie redundant in einer eigenen Datenhaltung vorzuhalten. Dieser
Ansatz reduziert den Implementierungs- und Wartungsaufwand, geht jedoch potenziell mit einer
geringeren Antwortzeit gegenüber physischen Integrationssystemen mit eigener,
optimierter Query-Verarbeitung einher~\cite{Putrama2024}. Um dem entgegenzuwirken, wurde, wie in
Abschnitt~\ref{sec:info-ways} beschrieben, ein Cache-Mechanismus implementiert, der wiederholte
Anfragen an externe Datenquellen reduziert und dadurch insbesondere bei häufig aufgerufenen
Dashboards kürzere Ladezeiten ermöglicht~\cite{grafana2026datasourcecaching}.

In der folgenden Tabelle~\ref{tab:reaction-times-comparison} werden die Antwortzeiten der
einzelnen Datenquellen mit und ohne aktivierten Cache verglichen. Es zeigt sich deutlich, dass
beim erstmaligen Abrufen der Daten dieselbe Zeit anfällt wie ohne Cache, da noch kein
Cache-Eintrag vorliegt. Da die Daten der einzelnen Quellen jedoch, wie in
Kapitel~\ref{sec:defined-sources} beschrieben, jeweils eine unterschiedliche Gültigkeitsdauer
besitzen, müssen sie nicht bei jeder Anfrage erneut von der externen Datenquelle abgerufen werden und können
direkt von der Cache Ebene geholt werden.

\begin{table}[H]
    \centering
    \begin{tabular}{lrrl}
        \toprule
        \textbf{Datenquelle} & \textbf{Mit Cache Ebene} & \textbf{Ohne Cache Ebene} & \textbf{Zugriffsart} \\
        \midrule
        MSSQL      & \SI{50}{\milli\second}            & \SI{50}{\milli\second}            & SQL-Abfrage \\
        Meraki     & \SIrange{50}{1070}{\milli\second}          & \SIrange{700}{1070}{\milli\second}             & \gls{rest}-API \\
        Zabbix     & \SIrange{2}{7}{\second}           & \SIrange{5}{7}{\second}            & \gls{jsonrpc}-API \\
        Silverpeak & \SIrange{100}{700}{\milli\second} & \SIrange{400}{700}{\milli\second}  & \gls{rest}-API \\
        \bottomrule
    \end{tabular}
    \caption{Vergleich der Antwortzeiten je Datenquelle mit und ohne aktivierten Cache}
    \label{tab:reaction-times-comparison}
\end{table}

Aus den Messwerten geht hervor, dass \gls{zabbix} im Vergleich zu
den anderen Datenquellen eine deutlich höhere Antwortzeit aufweist. Dies
ist unter anderem darauf zurückzuführen, dass ein Teil der von der
Anwendung abgefragten Werte bereits innerhalb von Zabbix aus vorhandenen
Messwerten berechnet wird. Solche Berechnungen werden gemäß der
\gls{zabbix}-Dokumentation durch den \gls{zabbix}-Server durchgeführt und können
beispielsweise auf einzelnen Messwerten oder auf aggregierten Werten
mehrerer Items basieren \cite{zabbix2026calculateditems}. Bei umfangreicheren
Berechnungen kann dies die Verarbeitung auf dem Zabbix-Server zusätzlich
belasten.

\subsection{Meraki API Datenquelle}
\label{subsec:meraki-ds-api}

\gls{merakicompany} stellt eine API für den Abruf von Informationen über
Meraki-Netzwerkgeräte bereit, die bereits in Abschnitt~\ref{subsec:meraki-api}
beschrieben wurde. Die über die API abgerufenen Informationen werden im
Plugin zur Darstellung der in den Abschnitten~\ref{par:device-info} und
\ref{par:device-clients} beschriebenen Werte verwendet.
Für die Erfassung der benötigten Informationen werden folgende API-Endpunkte
verwendet:

\begin{compactitem}
    \item \texttt{/organizations/\{organizationId\}/devices/statuses}
    zur Abfrage des Status und weiterer Informationen zu den Geräten einer
    Organisation,
    \item \texttt{/organizations/\{organizationId\}/networks}
    zur Abfrage der in einer Organisation vorhandenen Netzwerke,
    \item \texttt{/devices/\{serial\}/clients}
    zur Abfrage der mit einem Netzwerkgerät verbundenen Endgeräte.
\end{compactitem}

Die abgerufenen Daten werden anschließend den jeweiligen Standorten und
Netzwerkgeräten zugeordnet und für die Darstellung im Plugin aufbereitet.
Um die Anzahl wiederholter Anfragen an die \gls{merakiapi} zu reduzieren,
werden die abgerufenen Daten zwischengespeichert.

\paragraph{Gültigkeitsdauer}
\label{par:meraki-validation-time}

Für die über die \gls{merakiapi} abgerufenen Daten wurde eine
Cache-Gültigkeitsdauer von einer Stunde festgelegt. Die Wahl dieser Dauer
basiert auf den im bestehenden System vorliegenden Datensätzen. Dabei wurde
berücksichtigt, dass sich die für die Darstellung relevanten Informationen
zu den Netzwerkgeräten nur selten ändern. Eine kürzere
Cache-Gültigkeitsdauer würde daher zu häufigeren Anfragen an die
\gls{merakiapi} führen, ohne einen wesentlichen Mehrwert hinsichtlich der
Aktualität der dargestellten Informationen zu bieten.
Die gewählte Gültigkeitsdauer stellt somit einen Kompromiss zwischen der
Aktualität der dargestellten Informationen und der Reduzierung wiederholter
Anfragen an die \gls{merakiapi} dar~\cite{grafana2026datasourcecaching}.
