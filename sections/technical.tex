\section{Standortinformationen}
\label{sec:location-metric}

In dieser Arbeit werden unter Standortinformationen solche Informationen
verstanden, die einen Standort technisch beschreiben und allgemeine,
standortbezogene Eigenschaften zusammenfassen, die nicht unmittelbar
einem einzelnen System oder Gerät zuzuordnen sind. Sie ergänzen die in
den folgenden Abschnitten beschriebenen Netzwerk- und Systemmetriken
um Kontextinformationen zum jeweiligen Standort.

Dabei werden insbesondere Informationen berücksichtigt, die für die
eindeutige Identifikation, Klassifikation und geografische Einordnung
eines Standorts relevant sind. Diese Informationen ermöglichen es,
Standorte eindeutig zuzuordnen und auf einer Weltkarte darzustellen.
Zusätzlich wird der Status der zugrunde liegenden Datenquellen erfasst,
um nachvollziehen zu können, ob die Standortinformationen vollständig
und fehlerfrei abgerufen werden konnten.

\begin{compactitem}
    \item \textbf{Ländercode:} Der Ländercode gibt die Länderzuweisung eines
    Standorts nach dem Standard \gls{iso3166}~\cite{iso2026countrycodes} an.

    \item \textbf{Geografische Position:} Beschreibt die geografischen Koordinaten
    eines Standorts. Sie ermöglichen die eindeutige geografische Zuordnung und
    die Darstellung des Standorts auf einer Weltkarte.

    \item \textbf{Klassifikation:} Die Klasse eines Standorts lässt sich in
    folgende Kategorien unterteilen:
    \begin{compactitem}
        \item Cloud Hub
        \item Hub
        \item Remote Site
        \item Small Site
        \item Medium Site
        \item Large Site
        \item Special Site
    \end{compactitem}

    \item \textbf{Abrufstatus je Datenquelle:} Beschreibt für jede der zugrunde
    liegenden Datenquellen, ob die benötigten Standortinformationen erfolgreich
    abgerufen werden konnten oder bei der Erfassung ein Fehler aufgetreten ist.
\end{compactitem}

\section{Netzwerkmetriken}
\label{sec:netzwerkmetriken}

Netzwerkmetriken beschreiben den aktuellen Zustand und die Leistungsfähigkeit
eines Netzwerks. Sie ermöglichen eine Bewertung der Netzwerkkommunikation
und können dazu beitragen, potenzielle Probleme und Abweichungen frühzeitig
zu erkennen~\cite{aruba2026userguide}.

Für die Darstellung im Plugin wurden Netzwerkmetriken ausgewählt, die einen
schnellen Überblick über die Leistungsfähigkeit, Verfügbarkeit und
vorhandene Redundanz eines Standorts ermöglichen, ohne dass hierfür die
einzelnen Systeme betrachtet werden müssen. Zusätzlich werden die
entsprechenden Einzelwerte der überwachten Systeme erfasst, um bei Bedarf
eine detailliertere Betrachtung der Netzwerkinfrastruktur zu ermöglichen.

\subsection{Aggregierte Standortwerte}
\label{subsec:netzwerk-aggregierte-werte}

Die folgenden Metriken stellen aggregierte Werte auf Standortebene dar.
Sie werden aus den einzelnen Netzwerkmetriken der einem Standort
zugeordneten Systeme ermittelt. Die Aggregation dient dazu, den Zustand
der Netzwerkinfrastruktur eines Standorts unabhängig von der Anzahl der
einzelnen überwachten Systeme kompakt darzustellen. Die Aggregation von 
Messwerten dient der Verdichtung großer Datenmengen und ermöglicht die 
Darstellung komplexer Systemzustände in komprimierter Form \cite{wen2020aggregation}.

\begin{compactitem}
    \item \textbf{Bandbreite:} Die durchschnittliche Bandbreite beschreibt die
    durchschnittliche Datenübertragungsrate, die über ein Interface innerhalb
    eines bestimmten Zeitraums beim Senden oder Empfangen von Daten erreicht
    wird \cite{aruba2026userguide}.

    \item \textbf{Latenz:} Die Latenz beschreibt die Zeit, die Daten für
    die Übertragung zwischen zwei Geräten benötigen~\cite{aruba2026userguide}.

    \item \textbf{Erreichbare Geräte:} Die Anzahl der erreichbaren
    \glspl{silverpeak} an einem Standort~\cite{aruba2026userguide}.

    \item \textbf{Nichterreichbare Geräte:} Die Anzahl der nicht erreichbaren
    \glspl{silverpeak} an einem Standort~\cite{aruba2026userguide}.

    \item \textbf{Primäre WAN-Verbindungen:} Die Anzahl der als primär
    konfigurierten \glspl{wan}, über die der reguläre Datenverkehr eines
    Standorts geleitet wird.

    \item \textbf{Backup-WAN-Verbindungen:} Die Anzahl der als Backup
    konfigurierten \glspl{wan}, die im Falle eines Ausfalls der primären
    Verbindung den Datenverkehr übernehmen.
\end{compactitem}

\subsection{Einzelwerte}
\label{subsec:netzwerk-einzelwerte}

\paragraph{SD-WAN System}
\label{par:sd-wan-values}

~

Die folgenden Werte werden für jedes einzelne \gls{sdwan}-System erfasst.
Sie beschreiben die Eigenschaften und den aktuellen Zustand des jeweiligen
Systems. Einzelne dieser Werte, insbesondere die Erreichbarkeit und der
WAN-Status, bilden die Grundlage für die Berechnung der aggregierten
Standortwerte (siehe Abschnitt~\ref{subsec:netzwerk-aggregierte-werte}).

\begin{compactitem}
    \item \textbf{Name:} Eindeutige Bezeichnung des \gls{sdwan}-Systems.

    \item \textbf{Typ:} Beschreibt die Art des überwachten Systems,
    beispielsweise SD-WAN-Router.

    \item \textbf{LAN-IP-Adresse:} Die interne IP-Adresse des Systems
    innerhalb des lokalen Netzwerks.

    \item \textbf{WAN-IP-Adresse:} Öffentliche beziehungsweise
    externe IP-Adresse der WAN-Schnittstelle.

    \item \textbf{Firmware-Version:} Version der auf dem System
    installierten Software beziehungsweise Firmware.

    \item \textbf{Erreichbarkeit:} Gibt an, ob das System aktuell über
    das Netzwerk erreichbar ist.

    \item \textbf{WAN-Status:} Beschreibt den aktuellen Status beziehungsweise
    die Rolle der WAN-Verbindung, beispielsweise als primäre oder
    Backup-WAN-Verbindung.
\end{compactitem}

\paragraph{Virtuelle Netzwerke}
\label{par:virtuel-networks}

~

Die folgenden Werte werden zur Identifikation und Einordnung eines virtuellen
Netzwerks sowie zur zeitlichen Nachvollziehbarkeit seiner Erfassung verwendet.
Sie werden aus den bereitgestellten Datenquellen ermittelt, die in
Abschnitt~\ref{sec:defined-sources} beschrieben sind. Die ausgewählten Werte
ermöglichen dabei sowohl die eindeutige Zuordnung eines virtuellen Netzwerks
als auch die Einordnung der zugehörigen Ressourcen und die Nachvollziehbarkeit
des Erfassungszeitraums.

\begin{compactitem}

    \item \textbf{Name:} Der festgelegte Name eines virtuellen Netzwerks.
    Er dient zur eindeutigen Identifikation und Zuordnung des virtuellen
    Netzwerks innerhalb der dargestellten Infrastruktur.

    \item \textbf{Ressourcengruppe:} Die dem virtuellen Netzwerk zugewiesene
    Ressourcengruppe, über die zusammengehörige Ressourcen logisch gruppiert
    und verwaltet werden. Sie ermöglicht die Zuordnung des virtuellen Netzwerks
    zu den weiteren zugehörigen Ressourcen.

    \item \textbf{Firstseen:} Der Zeitpunkt, zu dem das virtuelle Netzwerk
    erstmals erfasst wurde. Dieser Wert ermöglicht die zeitliche Einordnung
    des virtuellen Netzwerks und gibt Aufschluss darüber, seit wann es in den
    erfassten Daten vorhanden ist.

    \item \textbf{Lastseen:} Der Zeitpunkt, zu dem das virtuelle Netzwerk
    zuletzt erfasst wurde. Dadurch kann nachvollzogen werden, wann das
    virtuelle Netzwerk zuletzt in den bereitgestellten Datenquellen
    festgestellt wurde.
    
\end{compactitem}

\paragraph{Netzwerkgruppe}
\label{par:network-group}

Eine \gls{nsg} filtert den ein- und ausgehenden Netzwerkverkehr von Azure-Ressourcen
anhand einer Menge von Sicherheitsregeln \cite{microsoft2026nsg}. Die folgenden
Werte werden erfasst, da sie die Konfiguration und Wirkung einer Sicherheitsregel
beschreiben.

\begin{compactitem}

    \item \textbf{Name:} Der eindeutige Name der Sicherheitsregel
    \cite{microsoft2026nsg}. Er ermöglicht die Identifikation der Regel.

    \item \textbf{Richtung:} Gibt an, ob die Regel für ein- oder ausgehenden
    Datenverkehr gilt \cite{microsoft2026nsg}:
    \begin{compactitem}
        \item Inbound
        \item Outbound
    \end{compactitem}
    Dadurch lässt sich die Kommunikationsrichtung der Regel bestimmen.

    \item \textbf{Zugriffsart:} Legt fest, ob Datenverkehr zugelassen oder
    blockiert wird \cite{microsoft2026nsg}. Sie zeigt die Wirkung der Regel.

    \item \textbf{Protokoll:} Das von der Regel betroffene Netzwerkprotokoll,
    beispielsweise TCP, UDP, ICMP oder Any \cite{microsoft2026nsg}.
    Dadurch lässt sich die betroffene Kommunikation genauer bestimmen.

    \item \textbf{Quelle:} Die IP-Adresse, das CIDR-Suffix oder der Dienst-Tag,
    von dem der Datenverkehr ausgeht \cite{microsoft2026nsg}.
    Sie zeigt, von welcher Quelle die Kommunikation ausgeht.

    \item \textbf{Quellport:} Der Port oder Portbereich, von dem der
    Datenverkehr ausgeht. Dadurch lässt sich die betroffene Kommunikation
    genauer eingrenzen.

    \item \textbf{Ziel:} Die IP-Adresse, das CIDR-Suffix oder der Dienst-Tag,
    an den der Datenverkehr gerichtet ist \cite{microsoft2026nsg}.
    Dadurch lässt sich das Ziel der Kommunikation bestimmen.

    \item \textbf{Zielport:} Der Port oder Portbereich, an den der
    Datenverkehr gerichtet ist. Er ermöglicht eine genauere Bestimmung
    des betroffenen Netzwerkdienstes.

    \item \textbf{Standardregel:} Gibt an, ob die Regel von Azure automatisch
    angelegt wurde \cite{microsoft2026nsg}. Dadurch kann zwischen
    Standard- und eigenen Regeln unterschieden werden.

    \item \textbf{Status:} Gibt an, ob die Regel aktuell aktiv ist.
    Dadurch lässt sich erkennen, ob die Regel derzeit wirksam ist.

\end{compactitem}

\section{Systemmetriken}
\label{sec:systemmetriken}

Systemmetriken beschreiben den aktuellen Zustand, die Verfügbarkeit und
die Ressourcennutzung der an einem Standort betriebenen Systeme. Sie
ermöglichen eine Einschätzung, ob die vorhandenen Systeme ordnungsgemäß
betrieben werden und ob sich Auffälligkeiten oder Kapazitätsengpässe
erkennen lassen.

Für die Darstellung im Plugin wurde dabei zwischen aggregierten
Standortwerten und Einzelwerten der jeweiligen Systeme unterschieden:
Erstere ermöglichen eine schnelle Übersicht auf Standortebene, Letztere
eine detaillierte Untersuchung einzelner Systeme. Bei der Auswahl der
zugrunde liegenden Metriken wurden insbesondere folgende Aspekte
berücksichtigt:

\begin{compactitem}
    \item Erkennung aktueller Probleme und Auffälligkeiten
    \item Bewertung der Ressourcennutzung und verfügbaren Kapazitäten
    \item Bewertung der Verfügbarkeit der Systeme
    \item Erkennung sicherheits- und wartungsrelevanter Zustände
\end{compactitem}

\subsection{Aggregierte Standortwerte}
\label{subsec:system-aggregierte-werte}

Die folgenden Metriken stellen zusammengefasste Werte auf Standortebene
dar. Sie werden aus den Informationen der einzelnen Systeme eines
Standorts ermittelt. Die Aggregation ermöglicht es, den Zustand eines
Standorts unabhängig von der Anzahl der vorhandenen Systeme kompakt
darzustellen.

Für die Bewertung des Systemzustands sind insbesondere die Anzahl
vorhandener Systeme, aktuelle Probleme, fehlende Softwareaktualisierungen
und isolierte Systeme relevant. Diese Werte ermöglichen eine schnelle
Erkennung von Standorten, an denen eine weitere Untersuchung erforderlich
ist.

\begin{compactitem}

    \item \textbf{Problemanzahl:} Die Problemanzahl beschreibt die Anzahl
    der aktuell erkannten Probleme der Systeme eines Standorts.
    Sie ermöglicht eine schnelle Einschätzung des aktuellen
    Problemzustands und kann als Ausgangspunkt für eine detaillierte
    Untersuchung dienen~\cite{zabbix2026problemget}.

    \item \textbf{Anzahl fehlender Softwareaktualisierungen:} Diese
    Metrik beschreibt die Anzahl der Systeme beziehungsweise
    Softwareaktualisierungen, die an einem Standort noch ausstehen.
    Sie ermöglicht die Erkennung eines bestehenden
    Aktualisierungsbedarfs.

    \item \textbf{Isolierte Systeme:} Diese Metrik beschreibt die Anzahl
    der Systeme, die aufgrund eines Sicherheits- oder Betriebsereignisses
    vom restlichen Netzwerk isoliert wurden. Sie ermöglicht die
    Erkennung von Systemen mit eingeschränkter Netzwerkkommunikation.

    \item \textbf{Anzahl an Systemen:} Diese Metrik beschreibt die
    Gesamtzahl der an einem Standort erfassten Systeme und
    Systemressourcen. Sie ermöglicht eine Einordnung der Größe der
    Systemlandschaft und dient als Bezugsgröße für weitere aggregierte
    Werte.

    \item \textbf{Geräteanzahl pro Typ:} Diese Metrik beschreibt die
    Anzahl der vorhandenen Systeme beziehungsweise Geräte, gruppiert
    nach ihrem Typ. Sie ermöglicht eine schnelle Übersicht über die
    Zusammensetzung der Systemlandschaft eines Standorts.

\end{compactitem}

Die aggregierten Werte dienen dabei nicht dazu, die einzelnen Systeme
vollständig abzubilden. Vielmehr sollen sie eine schnelle Einschätzung
ermöglichen, ob ein Standort hinsichtlich Verfügbarkeit, Ressourcen,
Sicherheit oder Aktualisierungsstand auffällig ist. Bei einer
festgestellten Auffälligkeit können anschließend die Einzelwerte der
betroffenen Systeme betrachtet werden.

\subsection{Einzelwerte}
\label{subsec:system-einzelwerte}

Die Einzelwerte werden für die jeweiligen Systeme und Geräte eines
Standorts erfasst. Sie ermöglichen eine detaillierte Betrachtung des
Systemzustands und unterstützen die Identifikation der Ursache einer
auf Standortebene festgestellten Auffälligkeit.

Die Auswahl der Einzelwerte orientiert sich dabei an den Eigenschaften
der jeweiligen Systemtypen. Dadurch werden nur solche Informationen
dargestellt, die für die Bewertung des jeweiligen Systems relevant sind.

\paragraph{HCI Information}
\label{par:hci-information}

Die folgenden Werte beschreiben den aktuellen Betriebszustand und die
Ressourcennutzung eines \gls{hci}-Systems. Sie ermöglichen insbesondere
die Bewertung der verfügbaren Rechen-, Speicher- und
Datenspeicherkapazität.

\begin{compactitem}
    \item \textbf{CPU-Auslastung:} Beschreibt den Anteil der aktuell
    genutzten Rechenleistung. Sie ermöglicht die Erkennung einer
    erhöhten CPU-Auslastung und damit möglicher
    Kapazitätsengpässe~\cite{vmware2026vsan}.

    \item \textbf{RAM-Auslastung:} Beschreibt den Anteil des aktuell
    genutzten Arbeitsspeichers. Sie ermöglicht die Bewertung der
    Speicherauslastung des Systems~\cite{vmware2026vsan}.

    \item \textbf{Speicherauslastung:} Beschreibt den Anteil des
    verfügbaren Massenspeichers, der aktuell belegt ist. Sie ermöglicht
    die Erkennung eines erhöhten Speicherbedarfs~\cite{vmware2026vsan}.

    \item \textbf{Datenspeicher-Auslastung:} Beschreibt den Anteil des
    verfügbaren Datenspeichers, der aktuell genutzt wird. Sie ermöglicht
    die Bewertung der Kapazitätsauslastung des Datenspeichers.

    \item \textbf{Speicherbereitstellung:} Beschreibt das Verhältnis
    zwischen der insgesamt verfügbaren und der bereitgestellten
    Speicherkapazität. Dadurch kann die vorhandene Kapazitätsreserve
    eingeordnet werden.

    \item \textbf{Genutzte vSAN-Kapazität:} Beschreibt die aktuell
    belegte Speicherkapazität innerhalb des \gls{vsan}-Verbunds.
    Sie ermöglicht die Bewertung der aktuellen Auslastung und
    verfügbarer Kapazitätsreserven~\cite{vmware2026vsan}.
\end{compactitem}

\paragraph{HCI Konfigurationsdaten}
\label{par:hci-configurationdata}

Neben den aktuellen Auslastungswerten werden statische
Konfigurationsdaten eines \gls{hci}-Systems erfasst. Diese Werte dienen
nicht primär der Überwachung des aktuellen Zustands, sondern der
Einordnung der vorhandenen Hardware- und Speicherkapazität.

\begin{compactitem}

    \item \textbf{\gls{raid}-Stufe:} Beschreibt die verwendete
    Redundanz- und Speicherstrategie und ermöglicht eine Einordnung
    der Ausfallsicherheit.

    \item \textbf{Anzahl der \gls{hci}-Knoten:} Beschreibt die Größe
    des HCI-Verbunds und ermöglicht eine Einschätzung der vorhandenen
    Infrastruktur.

    \item \textbf{Anzahl virtueller Maschinen:} Beschreibt die Anzahl
    der auf dem HCI-System betriebenen virtuellen Maschinen und gibt
    einen Überblick über den Umfang der virtualisierten Umgebung.

    \item \textbf{CPU-Ausstattung:} Umfasst die Anzahl der CPU-Sockel,
    CPU-Kerne pro Sockel sowie die Gesamtzahl der verfügbaren
    CPU-Kerne. Diese Werte ermöglichen eine Einordnung der verfügbaren
    Rechenkapazität.

    \item \textbf{Arbeitsspeicher pro Knoten:} Beschreibt die verfügbare
    Arbeitsspeicherkapazität eines HCI-Knotens und ermöglicht einen
    Vergleich der vorhandenen Speicherausstattung.

    \item \textbf{Datenträgerkonfiguration:} Umfasst die Anzahl und
    Größe der Cache- und Kapazitätsdatenträger. Dadurch kann die
    vorhandene Speicherkonfiguration des HCI-Systems eingeordnet
    werden.

    \item \textbf{\gls{vsan}-Kapazität:} Beschreibt die insgesamt
    verfügbare Speicherkapazität des \gls{vsan}-Verbunds und dient
    als Bezugsgröße für die Bewertung der Speicherauslastung.

\end{compactitem}

\paragraph{Serverinformationen}
\label{par:server-values}

Bei der Auswahl der Servermetriken wurden insbesondere die aktuelle
Ressourcenauslastung, die Verfügbarkeit sowie sicherheits- und
wartungsrelevante Zustände berücksichtigt. Diese Aspekte ermöglichen
eine Bewertung des aktuellen Betriebszustands eines Servers und können
gleichzeitig auf einen bestehenden Handlungsbedarf hinweisen.

\begin{compactitem}

    \item \textbf{CPU-Auslastung:} Beschreibt die aktuelle Nutzung der
    verfügbaren Rechenleistung und ermöglicht die Erkennung einer
    erhöhten CPU-Auslastung~\cite{microsoft2026troubleshoot}.

    \item \textbf{RAM-Auslastung:} Beschreibt die aktuelle Nutzung des
    verfügbaren Arbeitsspeichers und ermöglicht die Erkennung einer
    erhöhten Speicherauslastung~\cite{microsoft2026troubleshoot}.

    \item \textbf{Speicherauslastung:} Beschreibt den aktuell belegten
    Massenspeicher und ermöglicht die Erkennung von
    Kapazitätsengpässen~\cite{microsoft2026troubleshoot}.

    \item \textbf{Defender-Status:} Beschreibt den aktuellen
    Betriebs- und Schutzstatus des Microsoft Defenders. Dadurch kann
    erkannt werden, ob der grundlegende Schutz des Systems aktiv ist.

    \item \textbf{Zabbix-Status:} Beschreibt die Verfügbarkeit und
    Erreichbarkeit des Servers aus Sicht von Zabbix. Dadurch kann
    zwischen einem verfügbaren und einem nicht erreichbaren System
    unterschieden werden~\cite{zabbix2026availability}.

    \item \textbf{Zabbix-Probleme:} Beschreibt die Anzahl der aktuell
    für den Server erkannten Probleme. Die Metrik ermöglicht eine
    schnelle Bewertung des Problemzustands~\cite{zabbix2026problemget}.

    \item \textbf{Anzahl fehlender Softwareaktualisierungen:}
    Beschreibt den bestehenden Aktualisierungsbedarf des Servers.
    Dadurch können Systeme mit ausstehender Wartung identifiziert
    werden.

    \item \textbf{Isolationsstatus:} Gibt an, ob ein Server vom
    restlichen Netzwerk isoliert wurde. Dadurch können Systeme mit
    eingeschränkter Kommunikation erkannt werden.

    \item \textbf{Isolationsart:} Beschreibt die Art der angewendeten
    Netzwerkisolierung und ermöglicht eine genauere Einordnung der
    bestehenden Einschränkung.

\end{compactitem}

\paragraph{Geräteinformationen}
\label{par:device-info}

Für Netzwerkgeräte wurden insbesondere Identifikations- und
Statusinformationen ausgewählt. Die Identifikationsinformationen
ermöglichen die eindeutige Zuordnung eines Geräts zu einem Standort
und die Einordnung seiner Funktion innerhalb der Infrastruktur. Die
Statusinformationen ermöglichen hingegen eine schnelle Bewertung der
aktuellen Verfügbarkeit eines Geräts.

\begin{compactitem}

    \item \textbf{Name:} Eindeutige Bezeichnung des Geräts zur
    Identifikation innerhalb der überwachten Infrastruktur.

    \item \textbf{Gerätetyp:} Beschreibt die funktionale Rolle des
    Geräts, beispielsweise Firewall, Router, Switch oder Access Point.

    \item \textbf{Modell:} Beschreibt das konkrete Hardwaremodell und
    ermöglicht die technische Einordnung des Geräts.

    \item \textbf{LAN-IP-Adresse:} Ermöglicht die Zuordnung des Geräts
    innerhalb des lokalen Netzwerks.

    \item \textbf{Öffentliche IP-Adresse:} Beschreibt den externen
    Netzwerkzugang des Geräts beziehungsweise des zugehörigen
    Netzwerks.

    \item \textbf{Status:} Beschreibt den aktuellen Betriebszustand
    des Geräts und ermöglicht die Erkennung nicht verfügbarer Geräte.

\end{compactitem}

\paragraph{Verbundene Endgeräte}

\label{par:device-clients}

Die Informationen zu verbundenen Endgeräten ergänzen die
Geräteinformationen um die aktuell an einem Netzwerkgerät
angeschlossenen Clients. Sie ermöglichen insbesondere die Zuordnung
von Endgeräten zu Netzwerksegmenten und die Nachvollziehbarkeit der
aktuellen Netzwerkstruktur.

\begin{compactitem}

    \item \textbf{IP-Adresse:} Die aktuell zugewiesene IP-Adresse des
    Endgeräts zur Identifikation innerhalb des Netzwerks.

    \item \textbf{MAC-Adresse:} Die Hardwareadresse der
    Netzwerkschnittstelle zur eindeutigen Zuordnung des Endgeräts.

    \item \textbf{VLAN:} Das dem Endgerät zugeordnete virtuelle lokale
    Netzwerk. Dadurch kann die Netzwerksegmentierung des Endgeräts
    nachvollzogen werden.

\end{compactitem}

\section{Zabbix}
\label{sec:zabbix}

\gls{zabbix} ist eine Open-Source-Monitoring-Software, mit der Server und
andere Systeme erfasst und deren Auslastung überwacht werden
können~\cite{zabbix2026about}. Darüber hinaus ermöglicht \gls{zabbix} über
Tags und Gruppen eine strukturierte Gruppierung der überwachten
Systeme~\cite{zabbix2026about}.

\subsection{Zabbix API}
\label{subsec:zabbix-api}

\gls{zabbix} verwendet \gls{jsonrpc} als Grundlage für die Kommunikation mit 
der API. Dabei werden Anfragen und Antworten im JSON-Format kodiert und über 
HTTP-POST-Anfragen an die API übermittelt~\cite{zabbix2026api}. Für die Authentifizierung 
stehen zwei Möglichkeiten zur Verfügung. Einerseits kann über die Methode \texttt{user.login} 
unter Angabe eines Benutzernamens und Passworts ein API-Token angefordert werden. Andererseits 
besteht die Möglichkeit, einen bereits über die Weboberfläche generierten, permanenten API-Token 
zu verwenden. Der verwendete Token muss anschließend bei jeder weiteren Anfrage mitgesendet werden, 
um auf die übrigen API-Endpunkte zugreifen zu können~\cite{zabbix2026api}.

Das Codebeispiel~\ref{lst:zabbix-request} zeigt eine Möglichkeit, wie die Host-Informationen abgerufen
werden können.

\begin{lstlisting}[language=Typescript, caption={Zabbix API Request}, label={lst:zabbix-request}]
const baseUrl = '...';
const apiToken = '...';

const request = {
    jsonrpc: '2.0',
    method: 'host.get',
    params: {
        output: ['hostid', 'host', 'name'],
        selectTags: 'extend',
        selectGroups: ['groupid', 'name']
    },
    auth: apiToken,
    id: 1
};

const response = await fetch(baseUrl, {
    method: 'POST',

\subsection{Silverpeak API}
\label{subsec:silverpeak-api}

\gls{silverpeakcompany} API stellt Informationen über \gls{rest} Endpunkte bereit. Die Authentifizierung erfolgt über ein \gls{sessioncookie}
und ein CSRF-Token welches 
bei nachfolgenden Anfragen mitgesendet werden muss, um den derzeitigen Zustand eines \gls{silverpeak} zu ermitteln~\cite{aruba2026userguide}.

Listing~\ref{lst:silverpeak-request} zeigt eine solche Anfrage, um den Zustand eines
\gls{silverpeak} abzufragen.

\begin{lstlisting}[language=Typescript, caption={Silverpeak API request}, label={lst:silverpeak-request}]
const username = '...';
const password = '...';
const baseUrl = '...';

function extractCookieValue(setCookieHeader: string, cookieName: string): string | undefined {
    const match = setCookieHeader.match(new RegExp(`${cookieName}=([^;]+)`));
    return match?.[1];
}

const loginResponse = await fetch(`${baseUrl}/gms/rest/authentication/login`, {
    method: 'POST',
    headers: {
        'Content-Type': 'application/json'
    },
    body: JSON.stringify({
        loginType: 0,
        user: username,
        password: password
    })
});

const loginSetCookie = loginResponse.headers.get('set-cookie') ?? '';
const sessionId = extractCookieValue(loginSetCookie, 'gmsSessionID');
const csrfToken = extractCookieValue(loginSetCookie, 'orchCsrfToken');

if (!csrfToken || !sessionId) {
    throw new Error('Login erfolgreich, aber Session-Cookie oder CSRF-Token fehlt.');
}

const cookieHeader = `gmsSessionID=${sessionId}; orchCsrfToken=${csrfToken}`;

const appliancesResponse = await fetch(`${baseUrl}/gms/rest/appliance`, {
    method: 'GET',
    headers: {
        'Cookie': cookieHeader,
        'X-XSRF-Token': csrfToken,
        'Content-Type': 'application/json'
    }
});

const data = await appliancesResponse.json();
console.log(data);
\end{lstlisting}

\section{Grafana}
\label{sec:grafana}

\gls{grafana} kann eingesetzt werden, um Daten verschiedener Systeme grafisch 
aufzubereiten und einheitlich anzuzeigen~\cite{grafana2026about}. Grafana wird 
dabei nicht nur in Unternehmensumgebungen eingesetzt, sondern auch in wissenschaftlichen 
Forschungsinfrastrukturen zur Visualisierung und Überwachung von Betriebs- und 
Messdaten in nahezu Echtzeit \cite{VBondar2025}. Die weite Verbreitung der 
Plattform zeigt sich auch an der Anzahl ihrer Nutzer:innen. Laut eigenen Angaben 
von Grafana Labs wird \gls{grafana} von mehr als 35 Millionen Nutzer:innen weltweit 
genutzt; mehr als 7.000 Unternehmen zählen dabei zu den zahlenden Kund:innen~\cite{grafana2026pressrelease}.

\subsection{Aufbau}
\label{subsec:grafana-buildup}

\gls{grafana} ist eine Plattform zur Visualisierung und Überwachung von
Daten aus unterschiedlichen Systemen. Die grundlegenden Bestandteile
von \gls{grafana} sind Datenquellen, Dashboards und Panels
\cite{grafana2026dashboardsoverview}. Diese Komponenten übernehmen
unterschiedliche Aufgaben innerhalb der Plattform.

Datenquellen stellen die Verbindung zu den zugrunde liegenden
Systemen und Datenbanken her. Sie definieren, aus welcher Quelle Daten
bezogen werden und über welche Schnittstelle auf diese zugegriffen
werden kann. \gls{grafana} stellt hierfür eine Vielzahl bereits
integrierter Datenquellen bereit. Für Systeme, die nicht durch eine
integrierte Datenquelle unterstützt werden, können zusätzliche
Datenquellen in Form von Plugins installiert oder selbst entwickelt
werden \cite{grafana2026datasources}.

Dashboards dienen der Zusammenstellung und Organisation von
Visualisierungen. Innerhalb eines Dashboards können mehrere Panels
angeordnet werden, die jeweils unterschiedliche Daten oder
Auswertungen darstellen. Panels bilden damit die eigentliche
Visualisierungsebene und können beispielsweise Tabellen,
Zeitreihen oder Statusinformationen darstellen
\cite{grafana2026dashboardsoverview}.

Neben der webbasierten Benutzeroberfläche stellt \gls{grafana}
verschiedene Programmierschnittstellen bereit. Über die
\gls{grafana}-HTTP-API können beispielsweise Informationen über
Benutzer:innen, Teams und andere Ressourcen programmatisch abgerufen
oder verändert werden \cite{grafana2026httpapi}. Darüber hinaus können
Plugins eigene Datenzugriffe und Funktionen bereitstellen.

Für die vorliegende Arbeit ist insbesondere die Möglichkeit relevant,
Datenquellen innerhalb eines Plugins über die \gls{grafana}-API
anzusprechen. Dadurch kann die Anwendung auf bereits in
\gls{grafana} konfigurierte Datenquellen zugreifen, ohne für jede
Datenquelle eine eigene direkte Verbindung implementieren zu müssen.

Die grundlegende Struktur lässt sich somit in drei funktionale
Bereiche unterteilen:

\begin{compactitem}
    \item \textbf{Datenhaltung und Datenanbindung:} Datenquellen
    stellen die Verbindung zu den zugrunde liegenden Systemen und
    Datenbanken her.
    
    \item \textbf{Verarbeitung und Abfrage:} Über Abfragen werden die
    benötigten Daten aus den Datenquellen angefordert und für die
    weitere Verarbeitung bereitgestellt.
    
    \item \textbf{Visualisierung:} Dashboards und Panels stellen die
    abgerufenen und verarbeiteten Daten für die Benutzer:innen dar.
\end{compactitem}

Darüber hinaus ermöglicht die Plugin-Architektur die Erweiterung
dieser Funktionen. Plugins können sowohl Funktionalitäten für die
Benutzeroberfläche als auch eigene Backend-Komponenten bereitstellen.
Ein Backend-Plugin wird dabei als eigenständiger Prozess ausgeführt
und kommuniziert über \gls{grpc} mit dem \gls{grafana}-Server
\cite{grafana2026backendplugins}.

\subsection{Datenquellen}
\label{subsec:grafana-datasources}

Datenquellen ermöglichen den Abruf und die Verarbeitung von Daten aus
unterschiedlichen Systemen. \gls{grafana} verfügt bereits über eine
Vielzahl integrierter Datenquellen. Für weitere Systeme können
zusätzliche Datenquellen in Form von Plugins installiert oder
eigenständig entwickelt werden \cite{grafana2026datasources}.

Eine Datenquelle kapselt dabei die technische Anbindung an das
jeweilige Zielsystem. Dadurch kann \gls{grafana} Daten aus
unterschiedlichen Systemen über eine einheitliche Schnittstelle
bereitstellen. Die konkrete Kommunikation mit dem zugrunde liegenden
System bleibt dabei innerhalb der jeweiligen Datenquelle gekapselt.

Im Rahmen dieser Arbeit wird zwischen Datenquellen, die bereits in
\gls{grafana} konfiguriert sind, und Systemen unterschieden, auf die
die Anwendung direkt zugreift. Für bereits in \gls{grafana}
vorhandene Datenquellen erfolgt der Zugriff über den zentralen
\gls{grafana}-Endpunkt \texttt{/api/ds/query}. Dieser nimmt eine
Abfrage entgegen, leitet sie an die konfigurierte Datenquelle weiter
und stellt das Ergebnis der Anwendung zur Verfügung
\cite{grafana2026httpapi}.

Dadurch kann beispielsweise eine in \gls{grafana} konfigurierte
MSSQL-Datenquelle verwendet werden, ohne dass das Plugin selbst eine
direkte Verbindung zu dem MSSQL-Server aufbauen muss. Die Anwendung
kommuniziert stattdessen mit \gls{grafana}, während \gls{grafana} die
Weiterleitung und Ausführung der Abfrage übernimmt.

Ein möglicher Aufruf einer konfigurierten Datenquelle ist in
Codebeispiel~\ref{lst:grafana-datasource-request} dargestellt.

\begin{lstlisting}[language=Typescript, caption={Abfrage einer konfigurierten Datenquelle über die Grafana-API}, label={lst:grafana-datasource-request}]
import { getBackendSrv } from '@grafana/runtime';

async function queryDatasource(datasourceUid: string, rawSql: string) {
    const response = await getBackendSrv().post('/api/ds/query', {
        queries: [
            {
                refId: 'A',
                datasource: { uid: datasourceUid },
                rawSql,
                format: 'table',
            },
        ],
    });

    console.log(response.results.A.frames);
}

queryDatasource('mssql-uid', 'SELECT TOP 10 * FROM dbo.Locations');
\end{lstlisting}

\subsection{Plugins}
\label{subsec:grafana-plugins}

\gls{grafana} bietet die Möglichkeit, die Plattform durch Plugins um
zusätzliche Funktionen zu erweitern~\cite{grafana2026pluginmanagement}.
Für die vorliegende Arbeit ist insbesondere die Möglichkeit relevant,
eigene Plugins zu entwickeln. Dadurch kann eine auf den Anwendungsfall
zugeschnittene Benutzeroberfläche innerhalb von \gls{grafana} umgesetzt
werden~\cite{grafana2026plugintutorials}.

Für die Umsetzung stehen verschiedene Plugin-Typen zur Verfügung. Für
die vorliegende Arbeit wurde ein App-Plugin gewählt, da dieses die
Entwicklung einer eigenen Benutzeroberfläche ermöglicht und verschiedene
Funktionalitäten innerhalb einer Erweiterung zusammengeführt werden
können. Dies ist für die vorliegende Anwendung relevant, da Informationen
aus unterschiedlichen Systemen in einer gemeinsamen standortbezogenen
Ansicht dargestellt werden sollen.

Darüber hinaus können Plugins auf die in \gls{grafana} vorhandenen
Datenquellen zugreifen. Dadurch können bereits in \gls{grafana}
konfigurierte Datenquellen verwendet werden, ohne für jede Datenquelle
eine eigene Anbindung innerhalb der Anwendung implementieren zu müssen.
Diese Möglichkeit war ein wesentlicher Grund für die Entscheidung,
die Anwendung als \gls{grafana}-Plugin umzusetzen.

Die konkrete Verwendung der \gls{grafana}-API und der Zugriff auf
konfigurierte Datenquellen werden in den folgenden Abschnitten
beschrieben.

\subsection{API}
\label{subsec:grafana-api}

\gls{grafana} kann über eine HTTP-API programmatisch angesprochen werden~\cite{grafana2026httpapi}. 
Diese ermöglicht es beispielsweise, Team- oder Nutzerinformationen aus bestehenden 
\gls{grafana}-Systemen abzurufen.

Ein möglicher Aufruf innerhalb eines Plugins ist in Codebeispiel~\ref{lst:grafana-request}
dargestellt.

\begin{lstlisting}[language=Typescript, caption={Abrufen von Teaminformationen über die Grafana-API}, label={lst:grafana-request}] 
import { getBackendSrv } from '@grafana/runtime';

async function loadTeams() {
    const response = await getBackendSrv()
        .get('/api/teams/search', {
            query: '', perpage: 20,
        });
    console.log(response.teams);
}

loadTeams();
\end{lstlisting}

Die Schnittstelle kann mithilfe des \gls{grafana} Plugin SDK für Go erweitert werden, 
um eigene Plugins oder Datenquellen zu entwickeln~\cite{grafana2026plugintutorials,grafana2026backendplugins}.
Ein solches Backend-Plugin läuft dabei als eigenständiger Prozess, mit dem der 
\gls{grafana}-Server über \gls{grpc} kommuniziert~\cite{grafana2026backendplugins}.

Im Beispiel~\ref{lst:grafana-go-datasource} wird die grundlegende Verarbeitung einer 
Datenabfrage innerhalb eines Datenquellen-Plugins dargestellt.

\begin{lstlisting}[language=Go, caption={Minimale Verarbeitung einer Datenabfrage in Go}, label={lst:grafana-go-datasource}]
package plugin

import (
    "context"

    "github.com/grafana/grafana-plugin-sdk-go/backend"
    "github.com/grafana/grafana-plugin-sdk-go/backend/instancemgmt"
)

type Datasource struct{}

func NewDatasource(ctx context.Context, settings backend.DataSourceInstanceSettings) (instancemgmt.Instance, error) {
    return &Datasource{}, nil
}

func (d *Datasource) QueryData(ctx context.Context, req *backend.QueryDataRequest) (*backend.QueryDataResponse, error) {
    response := backend.NewQueryDataResponse()

    for _, query := range req.Queries {
        response.Responses[query.RefID] = backend.DataResponse{}
    }

    return response, nil
}
\end{lstlisting}
